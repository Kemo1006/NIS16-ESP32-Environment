- nov. 5, 2026 (Angelo's laptop, latest 15) — **WHY RETRY RATE CAME FROM THE SNIFFER, NOT THE BOARDS, vs RSSI (explanation + panel answer; no files/data changed).** Why: user was confused how RSSI is logged on the boards but MAC retry is not, and whether 'the work is fake'. **Facts:** (1) RSSI is handed to our code by the Wi-Fi driver, so the boards log it. (2) The driver resends frames itself and keeps its own retry counter inside Espressif's closed-source library; no public API returns it (D-15, checked sep. 27: `esp_wifi_statis_dump()` only prints); our code only sees `esp_mesh_send()` success/fail, so `retry_count` is an application-layer counter. (3) In normal mode the driver reads the frame header (incl. the Retry bit) for its own work but strips it before handing the payload up; the API has no field for it. (4) The sniffer runs in monitor mode (ESP-IDF name: promiscuous mode, `esp_wifi_set_promiscuous*`, a public documented feature) which passes whole raw frames, so `pcap_retry.py` counts Retry-flag frames per link/phase itself: a rate rebuilt from overheard frames, not the driver's counter, and it can miss frames. (5) Not fake: attacks are application-layer by design (D-20), so RSSI/MAC retry stay flat. **Why nodes are NOT put in promiscuous mode (panel answer; these are EXPECTED risks, NEVER TESTED, do not say 'we tried it'):** it makes data messy (each node hears only its neighbours, several nodes log the same frame, foreign Wi-Fi in busy places mixes in), loads the node CPU and could distort probe timing/PDR, could upset the mesh library (parent changes would look like attack effects), still would not give a node's own retries, and needs a recapture of every run + OK to touch frozen firmware (D-41). Normal-mode nodes log only their own sent/received work = clean. One external sniffer leaves the mesh unchanged. Per-node promiscuous counting = Future Work. **Slide sentence:** 'RSSI is reported by the driver; the MAC retry count is not exposed on the node, so we measured it with a sniffer.' ⚠️ Function names above are from general ESP-IDF knowledge, not checked against the installed IDF; confirm in the docs ('Wi-Fi Driver > Sniffer Mode') before they go in the paper. **API point (user asked 'how can promiscuous read the whole frame if there is no API?'):** there is NO API for the driver's retry COUNTER, but promiscuous mode is its own separate API set (`esp_wifi_set_promiscuous`, `..._rx_cb`, `..._filter`) that hands the callback the whole raw frame; normal-mode calls (`esp_mesh_recv`) return payload only. So the sniffer uses the raw-frame API and counts the Retry bits itself. Related: D-15, D-20, D-43, checklist A15.
