## 🐛 Four bugs found and fixed

### 1. 🚨 Silent arrivals-data loss — `trim_run.py` (CRITICAL)

The root's `*_arrivals.csv` export contained **two concatenated streams**: a full copy of
`telem.csv` (5,623 rows, 11 cols) followed by the real arrivals stream (2,368 rows, 14 cols),
each with its own header. This happens when an `EXPORT_LOGS` stream's `END_OF_FILE` marker is
corrupted — the host keeps capturing and the next stream lands in the same file.

`trim_run.py` split on timestamp regressions and kept the **longest** segment — the telemetry
copy. **The trimmed arrivals file came out byte-identical to the trimmed telem file: right name,
right size, zero arrival rows.** `features.py` then died with `KeyError: 'src_mac'`.

**Fixed:** the trimmer now splits on **schema first**, keeping only the block matching what the
filename promises. It also reports the second form of the same glitch — one file streamed twice
(`repeated capture: N header block(s), all telem schema`), hit on the 2026-07-26 root telem export.
`features.py` raises a specific error instead of a bare `KeyError`, and `export_logs.py` warns at
capture time. **Nothing was ever lost on disk** — the raw captures always held every row.

### 2. 🚨 Incomplete `trimmed/` folder — `trim_run.py`

Files needing no trimming were **not copied** into `trimmed/`, so a clean single-session capture
never reached the analysis input. Hit on the blackhole run: `trimmed/` had 6 of 7 files.
This does **not** raise — it silently NaNs out **PDR, LatencyHopRatio and TunnelLatency**.

**Fixed:** clean files are copied as-is, and the summary prints `files in output : 7 of 7`.

### 3. 🔧 `run_matrix.py --record` — three separate defects

| 🐛 | Bug | Symptom |
|---|---|---|
| **a** | `--outdir` defaulted to `exports` relative to **CWD** | `python tools\run_matrix.py` from repo root → *"No exported CSVs found"* for a fully captured cell |
| **b** | Counted children by `victim_` prefix only | Exporter writes `child_*` (`--role child` is the default) → `victim_telems=0`, refused to record |
| **c** | Validated the **raw** folder, and `validate_integrity` recurses | 14 files checked for a 7-file run; the 6 raw files FAIL on the very timestamp regressions trimming removes |

**Fixed:** default resolves next to the script, both prefixes accepted, validation targets
`trimmed/`. Result: `7 file(s) — 6 PASS, 1 WARN, 0 FAIL` → **recorded**.

### 4. 🔧 `verify_topology.py` — false "baseline re-routing" failure

M3 asks two separate questions: converges within 60 s, **and** stable through the 5-min baseline.
The tool conflated them. Rows logged before the root's first broadcast are stamped
`PHASE_ID_BASELINE` by default, so each node's **initial parent acquisition** counted as a
baseline re-route. Every change was at t = 0–12.8 s, with zero re-parenting for the remaining
~470 s — the mesh was stable and the tool said otherwise.

**Fixed:** changes inside `PHASE_STABILISE_S` count as formation, reported separately,
`--stabilise-s 0` restores the old behaviour. Both runs now read
`Converged within 60s: YES` / `Baseline re-routing free: YES`.

## 🎯 M7 — two "firmware-blocked" features recovered, no re-capture needed

`root_main.c:329` logs `latency = now − pkt->send_ts_us`, mixing the **root's** clock with the
**victim's**. Both start at their own board's boot and are never synchronised, so the column is
`true_latency − constant_offset` — large and negative (−194 s seen). It looked unusable.

**The offset is constant per (arrivals file, src_mac), so it cancels under subtraction.** That
makes both features computable from data already on disk:

| Feature | Method | Result |
|---|---|---|
| **LatencyHopRatio** (Eq 4.14) | subtract the per-node minimum → relative one-way delay ÷ hop count | **2.4–2.8 ms/hop, flat across layers 2–6** — Eq 4.14's own "consistent ratio → normal forwarding" |
| **TunnelLatency** | spread between the two arrivals of one probe; offset cancels **exactly** | 541 duplicate pairs, median 12.2 ms; **102 of 109 populated rows on `gt_label = 2`** |

Also corrected: **ForwardingRatio / IngressEgressDelta / ConsistencyScore were mislabelled
"FIRMWARE GAP".** They are relay-node features and work correctly — they populate on the
attacker's windows in a blackhole run (**133/789 rows this run**), and are NaN elsewhere by design.

### 📐 Feature coverage per run type

| Run type | Populated | All-NaN (and why) |
|---|---|---|
| baseline | **10/16** | 3 relay (no attacker) + 3 tunnel (no wormhole) |
| blackhole | **13/16** | 3 tunnel (no wormhole) |
| wormhole | **13/16** | 3 relay (no blackhole attacker) |
| **combined matrix** | **16/16** ✅ | — |

> M7's criterion *"no feature is uniformly NaN"* is a statement about the **assembled dataset**,
> not about any single run. Every feature is populated by at least one run type.

## 🌆 Afternoon — r2 captured, and a near-loss

**`linear · blackhole · r2` is captured and recorded.** It cost a scare worth writing down.

### 🔥 Three boards could not read their own files

r2's exports for node2, node4 and node5 all failed identically:

```
[####################] 100.0%  0 B/1.1 MB  0 rows  0 B/s
```

The device announced a correct size (`ftell` worked) then sent `END_OF_FILE` with
**zero rows** (`fgets` returned NULL on the first call). Power-cycling did nothing —
the fault is in the filesystem, not a stuck handle.

**Cause:** the children were left powered through Phases 7–8 of r1, so `telem.csv`
reached **1.1 MB** for an 11-minute run that should produce ~490 KB — about 15,000
rows, ~25 minutes of logging. That filled SPIFFS past the point of readability.
This is **I-017 recurring**; r1 escaped it only because Phase 2's `-Wipe -Flash`
full-erases the chip first.

### 🆘 New tool: `recover_spiffs.py`

esptool dumps the raw `spiffs` partition, bypassing the ESP32's filesystem entirely,
and the CSV rows are extracted from the dump. **Recovered 6,334 rows from node5**, a
board that could not stream a single row.

The correctness rule cost a rewrite. Stripping page metadata then splitting on
newlines **welds the tail of one row onto the head of the next** and fabricates data
that passes a field-by-field regex — the first version invented **303 rows** and
flagged none. It now accepts only byte runs delimited by `\n` on *both* sides in the
raw flash: **5,105 rows, 0 corrupt** on the same test.

**70 % recovery is enough** — M6 downsamples to a 1 Hz grid, so a 10 Hz stream missing
30 % still yields a complete window set (134 windows kept, 1 discarded).

### 🩹 Then it happened again — the wrong number, twice

r2 was eventually re-run cleanly. Two more traps fired:

1. The root was booted with **`-Repeat 1`** instead of `2`. **Harmless** — on the
   manual route `-Repeat` is cosmetic (`run.ps1:321` a hint, `:362` the auto-export
   path we don't use). It touches no build flag, no firmware, no CSV column.
2. `--record … --repeat 1` then **re-recorded r1**. A complete r2 sat on disk while
   the matrix read 1/24, and nothing complained.

Fixed by `run_matrix.py --autorecord`: it scans `exports/`, validates every capture
that isn't ticked off, and records it — no flags to mistype. `--status` now warns
about captured-but-unrecorded cells on its own.

### 🔭 And a way to see it coming

`board_check.py` now reports **SPIFFS usage** and **which firmware variant** is
flashed. Both need `--wait 75`: `mesh_setup_init()` blocks up to
`PHASE_STABILISE_S` = 60 s when there is no mesh to join, and both lines are logged
after it returns.

| reading | meaning |
|---|---|
| under ~10 % | clean |
| ≥ 50 % | ⚠️ will likely fail the export |
| 70 % | the I-017 board |

### 🧹 Housekeeping

- `export_logs.py --outdir` was the **fourth** tool defaulting to a CWD-relative
  `exports`, and the only one that *writes*. It had filed a whole baseline-tree run
  into `root_node\exports\` where no analysis command looks. All four now resolve
  next to their own script; the misfiled captures were SHA-256 verified as
  duplicates of archived copies before removal.
- Raw captures are now tracked in git (~6 MB), with `_archive/`, `trimmed/` and

## ✅ Fixed — the validator now reports the blackhole instead of warning about it

`validate_integrity.py` used to WARN three times on every healthy blackhole arrivals file:

```
WARN: phase 0 (baseline) has 1436 rows, expected ~3000 at 10.0 Hz (ratio 0.48 < 0.5) — possible truncation
WARN: phase 1 (blackhole) has 0 rows — expected ~1800 (missing phase, possible truncation)
WARN: phase 3 (cooldown) has 483 rows, expected ~1200 at 10.0 Hz (ratio 0.40 < 0.5) — possible truncation
```

**That zero *is* the deliverable** — no probes reaching the root during the attack window is the
blackhole signature M2 defines. The validator was applying its 10 Hz sample-coverage rule to an
**event log**: arrivals are per-probe records, so the row count tracks the *probe* rate (~4 Hz for
four victims), and 4 ÷ 10 lands under the 0.5 tolerance on every phase, every repeat.

`_check_arrivals_coverage()` now handles `*_arrivals.csv` separately. It measures the probe rate
per phase and tests truncation against **that run's own baseline rate**, so there is no fixed
nominal to be wrong about:

```
[PASS] root_node1_linear_blackhole_r3_..._arrivals.csv
    info: phase 0 (baseline): 1436 probes from 4 victim(s) over 360s = 3.98/s (reference rate)
    info: phase 1 (blackhole): 0 probes reached the root — total drop, the expected attack signature
    info: phase 3 (cooldown): 483 probes from 4 victim(s) over 120s = 4.01/s (101% of baseline)
```

`info:` never affects status. The checks it still WARNs on are the ones that would otherwise pass
silently — a missing baseline or cooldown, a cooldown rate collapsed against its own baseline, a
victim that probed at baseline and never returned, and **probes still arriving during the attack
window** above 50 % of baseline, which means the drop never took hold.

### 🪞 …then the same check called a perfect wormhole broken

The very first wormhole capture tripped the new leak warning:

```
WARN: phase 2 (wormhole): 901 probes still reached the root at 5.00/s = 125% of
      baseline — the attack did not take effect
```

**The check was wrong, not the run.** It was written against the blackhole, where the
attack means packets *stop*. A wormhole does the opposite: it **duplicates**. Node B's
probes are tunnelled over UART and replayed, so the root logs each one twice and arrivals
go *above* baseline. The 125 % was the tunnel working.

| phase | rows | unique `(src_mac, seq_num)` | duplicates | Node B `F4:2D:C9:73:E6:18` |
|---|---|---|---|---|
| 0 baseline | 1435 | 1435 | **0** | ×1.00 |
| 2 wormhole | 901 | 720 | **181** | **×2.00** |
| 3 cooldown | 461 | 461 | **0** | ×1.00 |

Multiplicity histogram for the attack window is `{1: 539, 2: 181}` — every double is
Node B's, and the other three victims hold ×1.00 throughout. Exactly the signature the
runbooks specify.

`ATTACK_SIGNATURE = {"blackhole": "drop", "wormhole": "duplicate"}` now selects the test:
the blackhole path keeps the leak check, the wormhole path counts duplicate
`(src_mac, seq_num)` deliveries and warns when there are **none** — the failure that
matters there, because a wormhole delivering one copy is indistinguishable from no attack.
Both paths verified against synthetic fixtures.

> 🧠 **The general lesson:** a validator that encodes "what a good run looks like" has to be
> told which *kind* of good run it is looking at. One attack's success criterion is the
> other's failure criterion.

### 🔬 Why "0 probes" is the attack and not a dead mesh

Worth having straight for the panel, because the topology makes it look wrong at first: the
blackhole sits at **layer 4**, yet the layer-2 and layer-3 victims — which reach the root without
traversing it — *also* go silent for the full 180.8 s window.

That is by design, not a mesh collapse. Victims are built with `BLACKHOLE_ROLE=1`, which addresses
their probes to `BLACKHOLE_ATTACKER_MAC` (`blackhole_victim.c:6-17`); the attacker relays them to
the root. Tree position is irrelevant — **every** victim funnels through the attacker at the
application layer. The attacker's own telemetry closes the loop:

| phase | probes received | tx (forwarded) | retry (dropped) |
|---|---|---|---|
| 0 baseline | 0 → 1439 | 0 → 1439 | 0 |
| 1 blackhole | 1439 → **2159** | **1439 → 1439** | 0 → **720** |
| 3 cooldown | 2159 → 2643 | 1439 → 1923 | 720 |

720 probes received during the attack, 720 dropped, zero forwarded — the victims never stopped
sending. Cooldown forwards 484, and the root logs 483 arrivals. Measured on both sides.

### ✅ The three habits that make the rest of the matrix routine

Every problem today traced back to one of these:

1. **Carry each child back UNPLUGGED.** Power them only when you're ready to boot the
   root. Leaving them on through Phases 7–8 is what filled SPIFFS and nearly cost r2.
2. **`board_check.py --port COMxx --wait 75` before a run.** If SPIFFS is ≥50 %,
   `-Wipe -Flash` that board first. Seconds now, versus losing an 11-minute run.
3. **`run_matrix.py --autorecord` instead of `--record`.** No flags to mistype, and
   nothing finished sits unticked.

And if a board ever returns `0 rows` again: **`recover_spiffs.py` BEFORE anything
wipes it.** That failure is no longer fatal.
