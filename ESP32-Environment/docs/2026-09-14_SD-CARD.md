# SD-Card Logging & Export Guide

> **Status: IMPLEMENTED.** Unlike the NIS16 branch this doc originated from, `combined`
> carries CC's working SD-card mirror — wired, debugged, and merged into the firmware
> (`components/mesh_common/src/sd_status.c` + the SD mirror inside `csv_logger.c`).
> Nothing here is a plan anymore; it's how logging actually works in this tree.

## Why we're doing this

- **Internal flash (SPIFFS) is tiny** (~500 KB/run cap) and USB export is slow: plug
  each board into the laptop and pull over serial, one at a time.
- **A microSD is gigabytes** and exports by **removing the card and copying files on a
  laptop** — all boards at once, no cables, no waiting.
- **Reminder (why you still need the board):** the ESP32 is what *creates* and *writes*
  the data. The card only *stores* it. The card helps at **export** time, not run time.
- Every board still logs to SPIFFS as before; the SD card is a **mirror**, not a
  replacement — a missing/failed card degrades to SPIFFS-only, it never blocks a run.

## Wiring (VSPI / SPI3_HOST)

Pin numbers are `SD_PIN_*` in `components/mesh_common/include/mesh_config.h`. Full
reference with the two gotchas below: `../../Setups/SD-CARD-WIRING.md`.

| SD reader pin | ESP32 pin | Constant |
|---|---|---|
| CS | GPIO5 | `SD_PIN_CS` |
| SCK | GPIO18 | `SD_PIN_SCK` |
| MOSI | GPIO23 | `SD_PIN_MOSI` |
| MISO | GPIO19 | `SD_PIN_MISO` |
| GND | GND | — |
| VCC | **VIN / 5V — not 3V3** | — |

> **Wormhole clash check:** the wormhole tunnel uses GPIO16/17. SPI SD (5/18/19/23)
> does **not** clash, so SD + wormhole coexist fine on the same board.

**Two gotchas that cost real bench time to find (see `Implementation Issues/SD-CARD-AND-WORMHOLE-WIRING.md` for the full debugging narrative):**

1. **VCC must go to VIN/5V, not 3V3.** The reader module has an onboard AMS1117-3.3
   regulator between VCC and the card; feeding it 3.3V leaves the card under-powered
   (~2.0–2.2V, below the ~2.7V an SD card needs). Symptom: `ESP_ERR_TIMEOUT` at the
   `ACMD41` mount step. Safe at 5V — the module's own level-shifter is powered from the
   regulator's 3.3V *output*, so the ESP32's GPIOs never see 5V.
2. **SPI clock is capped at 4 MHz** (`SD_MAX_FREQ_KHZ` in `mesh_config.h`), not
   ESP-IDF's ~20 MHz default — jumper wires can't reliably carry a full burst at 20 MHz.
   Symptom at the default speed: `ESP_ERR_INVALID_CRC` on `sdmmc_check_scr`, a few
   milliseconds after power-up succeeds.

## Format the card (one time)

FAT32 on the laptop (exFAT also works on newer ESP-IDF). Windows: right-click the
drive → Format → FAT32 → Quick Format. Then eject and insert into the ESP32's module.

## How logging works

- `sd_status_run_boot_check()` mounts the card at boot (non-fatal — telemetry always
  stays on SPIFFS regardless of mount result) and writes a boot report + a
  `<attack>/<topology>/<location>` folder tree, tracked in a `runs.csv` manifest.
- `csv_logger.c` mirrors every telemetry/arrivals row to the card alongside SPIFFS —
  same filenames and columns as before, so `preprocess.py`/`features.py` need no
  changes either way.
- **`SET_LOCATION=<home|G402|DLSU_Library|Goks>`** — a live serial command, and the
  value `run.ps1 -Location` passes ends up here. See `2026-09-14_LOCATIONS.md`.
- **`node_config.txt`** on the card (`nickname=`, `role=`) overrides the built-in MAC
  table in `node_identity.c` — useful for a spare/relabeled board.
- `CONFIG_FATFS_LFN_HEAP=y` must stay set in **both** `root_node/sdkconfig.defaults`
  and `child_node/sdkconfig.defaults` — without it, long folder names like
  `DLSU_Library` or `partial_mesh` fail to create (errno 22) and the mirror
  silently stops.

## Keeping the card tidy (ARCHIVE_SD, sep. 15, 2026)

Repeated test runs at the same `<attack>/<topology>/<location>` cell (e.g.
`blackhole/linear/home/`) used to pile up one `_telem.csv`/`_arrivals.csv` pair per
boot until the NEXT boot's own startup sweep moved the old ones into `_archive/`
(`sd_archive_prior_run_mirrors()` in `csv_logger.c`). Nothing was ever deleted — the
project's convention everywhere the SD mirror is at stake is "archive, never delete,
captures are irreplaceable" — but the run folder still looked cluttered between the
end of one run and the start of the next.

`export_logs.py` now closes that gap: `--archive-sd` sends a new `ARCHIVE_SD` serial
command right after a confirmed download, which moves THIS run's own mirror CSVs into
`<run_dir>/_archive/` immediately — same move logic as the boot-time sweep, just
triggered earlier. **`--delete` implies `--archive-sd`** (a good SPIFFS download is
already your signal that this capture is safe), so `run.ps1 -Clean` and `menu.ps1`'s
"Export a board only" flow (when you answer yes to "Wipe the board AFTER a good
download?") both get this for free — no new flag to remember. `--archive-sd` also
works standalone if you want the card tidied without wiping SPIFFS.

Firmware side: `csv_logger_archive_sd_now()` (declared in `csv_logger.h`) remounts the
card just long enough to do the move — `csv_logger_close()` has already unmounted it
by the time the serial export task can receive commands — and unmounts again after.
No-op (acked `ERROR:NO_SD_RUN`, never fatal to the export) if this boot never had an
SD run dir (no card / bad `location.txt`). Requires a firmware rebuild + reflash to
take effect; a board still running older firmware simply won't ack `ARCHIVE_SD` and
`export_logs.py` says so rather than failing the export.

⚠️ **Correction (sep. 25, 2026):** the importer and the USB listing (`LIST_SD`) both
**skip** `_archive/` — an earlier version of this paragraph said the opposite. Anything
in `_archive/` has to be copied out by hand.

## No boot-time archiving + no rows before the first phase (sep. 25, 2026)

**The bug:** these boards have one USB port for power AND data, so moving a board from
its powerbank to the laptop to export it — or the `idf.py monitor` → export handoff,
which toggles the reset line — REBOOTS it. The boot-time sweep then moved the run's
own CSVs into `_archive/`, and the new boot opened a fresh ~1 KB file of phase-255
rows that listed as "STILL RUNNING". The run was on the card but hidden (G402,
sep. 24 and 25).

**Now (needs a reflash):** `csv_logger_init()` no longer archives anything, and
`LOG_ONLY_DURING_RUN 1` (`mesh_config.h`) writes no rows — SPIFFS or SD — until the
boot knows a run is on. During the 60 s stabilisation window and the roster wait the
root sends a **PREPARE** signal every 5 s (`PHASE_ID_PREPARE`, not a phase); a node
that hears it starts logging, with rows still stamped **phase 255**, so the paper's
"Baseline Stabilization" record (layer, parent, parent switches, RSSI) is kept and
never labelled baseline. A node that missed every PREPARE starts at the first phase
0–3 it hears. TERMINATE never opens the log.

After the run the root sends no PREPARE, so a board rebooted onto the laptop writes
nothing and the run's file stays the newest one in its leaf, visible over USB and
on a pulled card. `ARCHIVE_SD` (above) is now the only way files reach `_archive/`.
Not recorded any more: rows from before the root starts stabilising, and rows from
before a child joins the mesh (it cannot hear PREPARE yet), so formation is timed
from the first PREPARE, not from boot. A log that starts inside a phase (missed
every PREPARE) gets convergence NOT MEASURED from `tools/verify_topology.py`. A board
that reboots mid-run starts a second file at the next phase it hears; the first
stays in the leaf, marked ABORTED. A rebooted ROOT starts a new stabilisation and
does log again, leaving a phase-255-only file that the tools already flag.

## The on-card `_r<N>_` is NOT your repeat number

The `_r<N>_` baked into a mirror CSV's filename on the card (e.g.
`victim_NODE_F42DC973E618_r23_b25_telem.csv`) comes from `sd_manifest_count_prior_runs()`
in `csv_logger.c` — a **lifetime count of every boot this physical board has logged at
this `<attack>/<topology>/<location>` folder**, test boots and MAC pre-flight checks
included. It has nothing to do with whatever repeat number you typed in the wizard or
`export_logs.py --repeat` — that value only tags the USB export filename, never reaches
the firmware, and the board has no way to know it. Seeing `r23` when you meant "this is
attempt 1" is expected on a board/location that's been used for weeks of testing, not a
sign anything mislabeled.

This is deliberate, not an oversight: a separate host-controlled counter could desync
from the card on a crash or power loss, so the firmware derives its number from the one
manifest (`runs.csv`) that can't drift out of sync with itself. The real repeat number is
assigned downstream instead — see Export below, and `import_sdcard.py --repeat`'s own
`--help`: *"The board cannot know it; it must match the `run_ledger.csv` entry."*

## Export (the payoff)

1. Finish the run; power the boards off.
2. Remove each microSD and put it in your laptop's card reader.
3. `python tools\import_sdcard.py --card E:\ --repeat N` — files the card's CSVs into
   `tools\exports\<attack>\<topology>\<location>\`, using the card's own `runs.csv` to
   resolve which boot belongs to which repeat. `--dry-run` previews without copying.
4. Re-insert the card before the next run.

USB export (`export_logs.py`, or `menu.ps1` → *Export a board only*) stays available as
a fallback, or for a board whose card you didn't pull.

## Testing / troubleshooting

1. Confirm the serial boot log prints the SD boot-check report (mounted / not present /
   error) — non-fatal either way.
2. Power off, pop the card, confirm the CSV tree and `runs.csv` are there and non-empty.
3. Run `python tools\validate_integrity.py` on the imported files — same checks as USB.
4. **Not yet hardware-verified:** `ARCHIVE_SD` (see "Keeping the card tidy" above) —
   compiles clean but has not been flashed/exercised on a real board yet. To verify:
   export with `--delete` (or `--archive-sd` alone), then pop the card and confirm
   this run's `_telem.csv`/`_arrivals.csv` moved into `<run_dir>/_archive/` rather
   than staying in the leaf folder or disappearing.
5. Mount failing? Isolate wiring from firmware first with a raw `CMD0` probe — see
   `Setups/SD-CARD-WIRING.md`'s continuity check.
