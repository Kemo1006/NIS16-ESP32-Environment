The contribution

What this project delivers

A dataset — not a detector.

We capture wireless mesh telemetry while two attacks run under controlled conditions, and publish it labelled, validated and documented so detection research can build on it.

What we claim

  • The data is real and cross-verified
  • Labels are produced by the experiment itself
  • Every capture passes integrity validation
  • Limitations are documented, not hidden

What we do not claim

  • No detection accuracy is reported
  • No thresholds or rules are derived
  • EDA is strictly descriptive (§4.2.6)
  • Classifier work is the next phase

Method — the key idea

Labels are produced by the experiment, not annotated after

PHASE 0 · BASELINE
300 s · gt_label 0
PHASE 1/2 · ATTACK
180 s · label 1 or 2
PHASE 3 · COOLDOWN
120 s · label 0

The root broadcasts the current phase ID over the mesh. Every node stamps that ID into every telemetry row it writes.

Why this matters for a dataset: the ground truth cannot drift from the data, because it was written by the same firmware, in the same row, at the same instant. No manual annotation step exists to get wrong.

Each run also carries its own benign reference — 420 s of labelled-benign traffic surrounding the attack window.

Analysis note

Why we show two projections, not one

Whole-mesh projection

Can the attack be seen in what every node measures?

Tunnel features are excluded — they exist on 2 of 6 nodes (~67 % NaN), above our 50 % cutoff. This is the realistic detection question.

Tunnel-end projection

Does the tunnel evidence itself separate the attack?

Restricted to the two tunnel-end nodes, with tunnel features retained — 854 windows on linear, 306 on star.

Showing only the first would look like there is no evidence. Showing only the second would overstate how easy detection is.

Both are honest answers to different questions. Neither replaces the other.

Engineering

Three silent corruptions — each now caught at source

Failure observed during collectionNow caught by
Device streamed the wrong file — telemetry saved under an arrivals name Schema checked at capture; file quarantined, --delete suppressed
Stale derived files left behind after a re-export Flagged when a raw source disappears
Duplicate capture double-counting one node Flagged before any analysis runs
The third produced no error at all. One node was counted twice — 264 windows against ~155 for every other node — and every total still looked plausible. That is the failure mode that matters most for a dataset, because nothing announces it.

Each guard fires at the moment the fault occurs, not twenty minutes later in the analysis. Each is documented with the incident that produced it.
